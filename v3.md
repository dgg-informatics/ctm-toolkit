# v3 update — knowledge sheet

Running record of everything going into the v3 update. Started 2026-11-02 on branch
`u/dane/clinical-genomic-split`. The work ships first as **2.4.0** (old names still work,
with deprecation warnings), gets tested and tweaked, and then becomes **3.0.0**: old names
removed, plus **one full database migration** of every stored trial.

---

## 1. Philosophy

- **Read anticipated fields, not the whole trial.** Each stage looks for specific fields in
  the normalized trial (criteria, long title, conditions, disease site, curator genes…) and
  sends each one to the AI as its own small piece of text. This gives better answers than
  sending the whole JSON trial, and uses far less context.
- **A missing field is fine.** If an expected field isn't there, the stage logs a warning
  and carries on. `parsed_sections` records `found: false` for it. It never errors.
- **Self-evident data.** Every suggestion says where its text came from (`source` = the
  field path), how its node was produced (`mapping_source`), whether it's clinical or
  genomic (`node_type`), and whether it ended up in the match clause
  (`transferred_to_match`).
- **One writer of match clauses.** Only `ctm-llm autofill-ctml` writes
  `treatment_list.step[0].match`. Everything before it only *suggests*.
- **Clinical and genomic are separate scans** with separate prompts, read in one place
  (`_llm_curation._ctml_suggestions`).

## 2. Commands

| Command | What it does | Reads | Writes |
|---|---|---|---|
| `ctm-mm trials` | Pull + normalize sources. **No longer pre-fills match clauses** (age/gender/diagnosis now come back as clinical entries) | sources | `00_raw_trials`, `01_normalized_trials` |
| `ctm-llm clinical` | Clinical CTML suggestions | `02_diff_trials` (`changed`) or `--trials` | `03_clinical_trials` |

| `ctm-llm autofill-ctml` **[beta]** | Builds the match clause from both stages' suggestions | `04_genomic_trials` | `04b_llm_autofill_trials` + the to-curate export (moved here from genomic) |

- `ctm-pre-curate` runs: `trials` → `trials-diff` → `clinical` → `genomic` → `autofill-ctml`.
- **Deprecated in 2.4.0, removed in 3.0.0:** `ctm-llm general` (→ `clinical`),
  `ctm-llm biomarkers` (→ `genomic`), `ctm-ctml` (→ `clinical`),

## 3. `_llm_curation` layout

```json
"_llm_curation": {
  "_ctml_suggestions":      [ <entry with a node>, ... ],
  "_null_ctml_suggestions": [ <entry with suggested_node null>, ... ],
  "molecular_genomic_refs": [ <ref>, ... ],
  "parsed_sections": {
    "clinical": { "<source>": {"found": bool, "scanned": bool, "pieces": int}, ... },
    "genomic":  { "<source>": {"found": bool, "scanned": bool, "pieces": int}, ... }
  },
  "stage_runs": {
    "clinical": {"ran_at": "<UTC ISO>", "processed_with": "ctm-llm clinical 2.4.0"},
    "genomic":  {"ran_at": "<UTC ISO>", "processed_with": "ctm-llm genomic 2.4.0"},
    "autofill": {"ran_at": "<UTC ISO>", "processed_with": "ctm-llm autofill-ctml 2.4.0"}
  },
  "autofill": { "method": "auto", "filled": bool, "reason": str, "nodes": int,
                "mixed_pieces": int, "diagnosis_sources": [<source>, ...],
                "match_sources": [<source>, ...],
                "mixed_logic": {"and": int, "or": int, "unresolved": int} }
}
```

`autofill.reason` is always set (added 2026-11-03; it used to be null on a fill):

| `filled` | `reason` |
|---|---|
| true | `filled empty match`: the normal first fill |
| true | `overwrote existing match`: `--overwrite` replaced a match that already existed |
| false | `match not empty`: an existing match was kept (no `--overwrite`) |
| false | `no suggestions`: nothing usable to write |
| false | `no treatment_list step`: nowhere to write |

### Entry fields

| Field | Values | Meaning |
|---|---|---|
| `source` | field path (table below) | Where the text came from in the trial |
| `text` | string | The exact text (or field value) that was mapped |
| `suggested_node` | CTML node or `null` | The suggestion. Null entries live in `_null_ctml_suggestions` |
| `node_type` | `clinical` \| `genomic` | Which stage wrote it. Each stage only replaces its own |
| `mixed` | bool | `true` when the same piece produced **both** a clinical and a genomic node. The and/or between them is a curator call |
| `mapping_source` | table below | How the node was produced |
| `transferred_to_match` | `null` → `true` / `false` | `null` until autofill runs; then `true` if used in the match, `false` if not. Stays `null` if autofill skipped the trial |
| `site_mappings` | list | Disease-site entries only: per-site mapping and where it came from |
| `mixed_logic` | `and` \| `or` \| `unresolved` | Set by autofill on both entries of a mixed piece (same source + text): how they were combined |

Nulls are recorded **per stage**. A criterion with a genomic node but no clinical node shows up
in `_ctml_suggestions` (genomic) **and** in `_null_ctml_suggestions` (clinical).

### `source` values (field paths)

| `source` | Trials that have it | Clinical | Genomic |
|---|---|---|---|
| `eligibility.inclusion` | all | AI, per top-level criterion (with its sub-criteria) | AI |
| `eligibility.exclusion` | all | AI | AI |
| `_summary.long_title` | all (CTGov `officialTitle` / AMC `<FULL_TITLE>`) | AI | AI |
| `_raw.minimum_age` | Sparrow, West, DDOTS | field value map | — |
| `_raw.sex` | Sparrow, West, DDOTS | field value map | — |
| `_raw.age_group` | AMC | field value map | — |
| `_raw.conditions` | Sparrow, West, DDOTS | keyword → OncoTree map | AI |
| `_raw.categorys` | AMC | AMC category → OncoTree map | — |
| `_raw.disease_site` | AMC | reviewed table → AI draft | — |
| `_raw._ddots.disease_site` | DDOTS (`sparrow-api`) | reviewed table → AI draft | — |
| `_raw._west.Disease Site` | West | reviewed table → AI draft | — |
| `_raw.octsu_genes_interest` | AMC | — | AI |

Not read: `_summary.short_title` (usually an acronym), `_summary.disease_keywords` (only
copies conditions / disease site), and the rest of `_raw._west` / `_raw._sparrow`.

### `mapping_source` values

| Value | Meaning |
|---|---|
| `ai` | AI prompt, validated in code |
| `reviewed_ref` | Reviewed disease-site table `src/ctm/refs/disease_site_oncotree.json` |
| `ai_draft` | AI-drafted disease-site row, not reviewed yet (cache) |
| `keyword_oncotree_map` | Conditions keyword list → OncoTree, no AI |
| `amc_category_oncotree_map` | AMC category table → OncoTree, no AI |
| `field_value_map` | Fixed rule on a field's value (`"18 Years"` → `">=18"`, `FEMALE` → `"Female"`, `Adults` → `">=18"`) |

### `molecular_genomic_refs`

```json
{"trial_nct", "reference": "<quoted snippet>", "biomarker": "MYCN",
 "type": "snv|cnv|fusion|msi|mmr|tmb|hrd|ihc|other", "section": "<source>",
 "in_kb": bool, "origin": "germline|somatic|unknown"}
```

- A wider net than genomic nodes: everything molecular the trial mentions, including what CTML
  can't express yet (TMB, HRD, IHC). This is the staging area for future genomic CTML.
- One ref per hit **per piece**: MYCN in two criteria gives two refs. `section` is set by code.
- Renamed from `biomarker_references`.
- `origin` is set by the AI from the piece's wording: `germline` for inherited ("germline",
  "hereditary"), `somatic` for tumor ("tumor-based NGS", "ctDNA"). MSI/MMR/TMB/HRD and IHC
  are tumor tests, so they're `somatic` even without tumor wording (added 2026-11-03, prompt
  `2c090034`). Anything else, including missing or junk values, is stored as `unknown`; there
  is no NA. It's a label only and doesn't change nodes or matching.
- **Worked example (real trial, 2026-11-03).** Long title "Phase II Randomized Trial of
  Radiotherapy With or Without Cisplatin for Surgically Resected Squamous Cell Carcinoma of
  the Head and Neck (SCCHN) With TP53 Sequencing":
  - Genomic node: `null`. TP53 sequencing is something the trial does, not an eligibility
    requirement, so a TP53 node would wrongly restrict the trial.
  - Ref: TP53 logged with `section: "_summary.long_title"`. Mentioned, recorded, not
    required. This is the intended split between nodes and refs.

### `stage_runs` vs `run_date`

- `run_date` (top-level on the trial) names the **weekly run**. Every stage inherits it from
  its input documents and never reads the clock, so one run's documents correlate across
  collections even when the stages run on different days. With `--trials` the file has no
  run date, so the first stage uses today.
- `_llm_curation.stage_runs.<stage>` records when **that stage** last ran on the trial (UTC)
  and which command and version wrote it. Each stage writes only its own key. Autofill records
  its run even when it skips the trial. Added 2026-11-03.

### `parsed_sections`

Every source the stage looks for, with `found` (the trial had text there), `scanned` (processed
this run) and `pieces` (pieces sent; for disease sites, the number of sites).

## 4. Genomic CTML rules (prompt + validator)

Trial-side keys:

| Key | Allowed values |
|---|---|
| `hugo_symbol` | HUGO gene symbol |
| `variant_category` | `Mutation` · `!Mutation` · `Copy Number Variation` · `Structural Variation` |
| `wildtype` | JSON `true` / `false` |
| `protein_change` | `p.` + HGVS, exact, case-sensitive (`p.V600E`) |
| `wildcard_protein_change` | `p.` + codon (`p.V600`) |
| `variant_classification` | `Missense_Mutation` · `Nonsense_Mutation` · `In_Frame_Del` · `Frame_Shift_Del` · `Splice_Site` |
| `exon` | integer |
| `cnv_call` | `High Amplification` · `Low Amplification` · `Homozygous Deletion` · `Heterozygous Deletion` |
| `mmr_status` | `MMR-Deficient` · `MMR-Proficient` |
| `ms_status` | `MSI-H` · `MSI-L` · `MSS` |

Wildtype matrix:

| Requirement | Node |
|---|---|
| Has a documented mutation | `Mutation`, `wildtype: false` |
| Confirmed wildtype (untested patients don't match) | `Mutation`, `wildtype: true` |
| **No documented mutation** — the standard exclusion | `!Mutation`, `wildtype: false` (wildtype + untested match) |
| CNV present / documented absent | `Copy Number Variation`, `wildtype: false` / `true` — **no `!`** |
| Fusion present | `Structural Variation`, `wildtype: false` — **no `!`, and never `wildtype: true`** |
| MSI / MMR | `ms_status` / `mmr_status` only — **no `variant_category`, no `wildtype`** |

- Every node with a `variant_category` carries `wildtype`. If it's missing, `false` is filled in.
- Fusion `wildtype: true` is invalid. Patient fusion docs exist only for detected fusions
  (`to_matchminer` skips `wildtype=TRUE` SV rows), and matchengine's fusion query ignores
  `WILDTYPE`. A fusion exclusion gets no node, only a ref.
- The validator drops a **whole leaf** when anything about it is invalid, rather than
  stripping one field, because stripping widens the requirement. That covers a bad value,
  gene-scoped keys without a valid gene, `!KRAS`, `!` on CNV/SV, or `wildtype` on MSI/MMR.

## 5. Clinical CTML

- Clinical-only prompt (`clinical_ctml.CLINICAL_SYSTEM_PROMPT`). Any genomic leaves the AI
  returns are stripped.
- `oncotree_primary_diagnosis` is checked against the live OncoTree list (`fix_oncotree_name`).
  `_SOLID_` / `_LIQUID_` are allowed as special values.
- Disease sites: reviewed table first, then the AI-draft cache (`.disease_site_cache.json`),
  then the AI. 10 or more sites collapse to `_SOLID_` / `_LIQUID_`. The table is seeded with
  the 22 DDOTS values; placeholders ("Multiple Disease Sites", "Genomic Based Trial"…) map to
  nothing. **Mappings are to be confirmed by a clinician.**

## 6. `autofill-ctml` rules

- Reads **only** `_llm_curation._ctml_suggestions`, never the raw trial.
- Uses every criterion node (`eligibility.inclusion` / `eligibility.exclusion`, both node types)
  plus the age/sex nodes.
- **Diagnosis = one OR of every positive `oncotree_primary_diagnosis` from every clinical
  source:** criteria, long title, conditions, AMC categories and all three disease-site fields.
  Duplicates are removed, and the OR goes first in the match.
  - A criterion node with a diagnosis plus other fields (e.g. + gender) gives its diagnosis to
    the OR and keeps the rest as its own node.
  - Negated diagnoses (`!Lung`) stay separate nodes, AND-ed with everything else.
  - `diagnosis_sources` in the report lists which sources contributed to the diagnosis OR.
    `match_sources` lists every source that contributed anything to the match, in match order
    (diagnosis sources first). It matches the entries marked `transferred_to_match: true`.
  - Decided by Dane, 2026-11-02, after a head and neck trial whose criterion gave
    "Squamous Cell Carcinoma, NOS" while conditions gave "Head and Neck Squamous Cell
    Carcinoma". All of them now go into the OR.
- **Genomic:** title, conditions and curator genes-of-interest genomic nodes are **always
  added** after the criteria's, with duplicates removed (Dane, 2026-11-03; previously only when
  no criterion had a genomic node).
- **Clinical from title / conditions:** only their diagnoses are used (into the diagnosis OR).
  Their other clinical fields (e.g. an age the AI read from the title) are ignored. Age and sex
  come from the criteria and the `_raw` age/sex fields.
- `ecog_score` is **suggested but never written to the match** (not used in matching yet).
- Identical nodes are collapsed. `match` is a **plain list of nodes**, since a top-level list
  is already AND-ed.
- **Mixed pieces**: a clinical and a genomic entry with the **same `source` and the same
  `text`**, from any source both stages read (criteria, long title, conditions). The clinical
  and genomic stages stay fully independent, so the and/or between them is decided here, by
  **one small AI call per mixed piece**, its only AI use. Dane chose this hybrid over a fully AI
  autofill on 2026-11-03.
  - `or` → one item `{"or": [clinical node, genomic node]}`. That piece's diagnosis stays inside
    it, not in the shared diagnosis OR.
  - `and` → both nodes are AND-ed, as before.
  - `unresolved` (junk answer, content filter, or no AI) → AND-ed, and flagged.
  - Recorded as `mixed_logic` on both entries and counted in the summary.
  - Cached in `.ctml_autofill_cache.json` (prompt hash + text + both nodes).
  - The AI client is created only when a trial actually has a mixed piece. `--yes` skips the
    cold-cache prompt, and `ctm-pre-curate --yes` passes it on.
- Within one node, `and`/`or` only combine leaves of the **same** type. Each stage strips the
  other type's leaves (`keep_clinical`, `validate_genomic_node`), so cross-type logic only
  exists between the two entries of a mixed piece.
- Every leaf gets `_CURATED_METHOD: "auto"`.
- Fills only empty match clauses unless `--overwrite`.

## 7. Caches

All live in `cache_dir()`: `$CTM_CACHE_DIR`, then `/var/lib/ctm/cache`, then
`$XDG_CACHE_HOME/ctm`, then `~/.cache/ctm`.

| File | Stage | Key |
|---|---|---|
| `.ctml_clinical_cache.json` | clinical | prompt hash + source + text, raw answer validated on read |
| `.ctml_genomic_cache.json` | genomic | same |
| `.disease_site_cache.json` | clinical | lowercased site → AI-drafted row (review, then copy into `refs/`) |
| `.ctml_autofill_cache.json` | autofill-ctml | prompt hash + text + both nodes → `and` / `or` / `unresolved` |

Editing a prompt automatically skips old cached answers. Renaming a `source` does too, since
it's part of the key. For a clean test run: `export CTM_CACHE_DIR=/tmp/somewhere`.

## 11. Parked for later releases

- **2.5.0 — parallel AI calls.** `clinical` and `genomic` call UMGPT one at a time: roughly
  55–65 calls per trial across both stages, about 1.5–3 minutes per trial on a cold cache. The
  plan is a thread pool with a `--workers` setting (modest default, since UMGPT's rate limit is
  unknown) and automatic retry on "too many requests". Cache keys, results and entry order stay
  the same. Expect roughly 5–8× faster cold runs. Not started — waiting on Dane.
- **Later — gene alias normalization.** Today `hugo_symbol` in genomic nodes is whatever the AI
  writes, usually but not always the official symbol, and patients' `TRUE_HUGO_SYMBOL` is copied
  verbatim from the genomic report (`to_matchminer.py`). matchengine compares them exactly, so
  `HER2` vs `ERBB2` (also HER3/ERBB3, c-MET/MET, c-KIT/KIT, PD-L1/CD274, MLL/KMT2A) silently fails
  to match. Plan: a reviewed `src/ctm/refs/gene_aliases.json`, applied in the genomic validator
  (and the prompt), and optionally to the patient biomarker column so both sides agree. Parked
  by Dane, 2026-11-03.
